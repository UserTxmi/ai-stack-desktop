# E11: mismo workspace, dos escritorios, una sola sesión de ensayo

**Pregunta:** ¿conserva el pequeño host Tauri/WebView2 la experiencia de OpenCode en Windows nativo tan bien como Desktop Electron/Solid? El binario A de `experiments/phase1/ui` solo abre `127.0.0.1:<puerto>`; no tiene IPC de aplicación, herramientas, actualizador ni instalador. B es el EXE oficial fijado en `versions.json`, no una imitación del chat. La prueba requiere pantalla y operador. **Estado: pendiente.**

1. En la VM de preparación, además de lo indicado en [1B](PHASE1A_REPORT.md), disponer de toolchain estable Rust MSVC x64, SDK y herramientas de compilación MSVC, WebView2 Evergreen. Son prerrequisitos del **laboratorio**, no del usuario. Desde la raíz, en PowerShell:

   ```powershell
   $p = (Resolve-Path experiments/phase1).Path
   $env:CARGO_HOME = "$p/.lab/cargo-home"
   $env:CARGO_TARGET_DIR = "$p/.lab/ui-target"
   cargo build --release --locked --manifest-path "$p/ui/Cargo.toml"
   ```

   Usar el `Cargo.lock` entregado; registrar `rustc -Vv`, build Windows y versión WebView2. Guardar snapshot. Preparar B en **otro clon** con el instalador upstream ya verificado `.lab/downloads/opencode-desktop-win-x64.exe`, sin aceptar upgrade a OpenCode 2. Desconectar la red externa antes del primer arranque de los componentes. El instalador upstream solo prepara el comparador B.
2. En cada clon ejecutar `py -3.12 -B experiments/phase1/run.py --isolated-offline --interactive`. Exigir las mismas aprobaciones del catálogo y del turno. El script muestra URL, contraseña efímera y carpeta `Proyecto de ensayo ñ` bajo el `run-*`. En A lanzar `& "$p/.lab/ui-target/release/ai-stack-ui-probe.exe" <puerto>` y autenticar como `opencode` en el origen local. Si no ofrece autenticación utilizable, registrar fallo de paridad, no pasar secretos en la URL.
3. En B seleccionar/conectar al servidor existente en el selector oficial con la misma carpeta y modelo. Registrar PID del proceso principal de cada escritorio en el Administrador de tareas. Si Desktop inicia además un servidor propio, medirlo, etiquetarlo y señalar incumplimiento de D2; no matar por nombre ni eliminarlo de las cifras para igualar el resultado. Si no permite conexión autenticada o usa otra sesión, no comparar latencias como si fueran el mismo montaje.
4. En cada brazo, tres rondas con perfil equivalente: 120 s en reposo, abrir proyecto, seleccionar `labcpa/lab-reasoner` y `high`, enviar una petición sintética, abrir terminal interna, crear un archivo de ensayo dentro del proyecto, cerrar terminal y reabrir sesión. Cancelar un turno y abrir/cerrar panel 20 veces. El proveedor normal no emite tool calls: para comparar la aprobación real, usar además el escenario `tools` del laboratorio interactivo. Registrar eventos, permiso denegado, foco/teclado, copia/pega, reconexión y cualquier descarga intentada (DevTools/Network con red externa desconectada). Los scripts de índices HTTP no prueban carga dinámica, fuentes o workers.
5. Desde una segunda PowerShell, `& "$p/measure-ui.ps1" -RootPid <PID> -Arm A -Seconds 120` (o `B`). Sin privilegios elevados. Medir también tiempo hasta UI utilizable con cronómetro y `metrics.jsonl` del backend. Calcular CPU en núcleos = ΔCPU_s/Δtiempo por identidad `(PID, creación)`; informar p50/p95 por escenario y dispersión, memoria privada, working set por proceso y procesos residuales tras salir. No sumar working sets como si fueran memoria privada. No contar dos veces el servidor si aparece también en el árbol de B. Registrar procesos compartidos sin atribución cierta por separado. Muestreo CIM es preliminar: anotar coste y repetir un control sin monitor.
6. Cerrar UI, pulsar Entrar en el laboratorio, verificar `cierre-*`; reabrir una vez para observar si reaparece algún proceso no previsto. Resultado por brazo: build, perfiles, hits/misses funcionales, duplicados, CPU/privada/latencias, archivos JSONL y limitaciones. Sin paridad de permisos, PTY, sesión o aislamiento, no elegir un shell por memoria. La aprobación final de D1 queda para revisión de los resultados.
