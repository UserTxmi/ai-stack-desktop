# Rendimiento: qué medir antes de elegir el shell

**V · Línea de referencia, no objetivo:** el informe Linux del 22-09-2026 registra aproximadamente **0,8 GiB** para OmniRoute (servidor + supervisor) y **0,75 GiB** para OpenCode. Cita picos de OmniRoute de 1 y 1,1 GiB en ventanas distintas y de CLIProxyAPI de 104,7 y 112,7 MiB. No reprodujo el episodio reportado de 12 GB. El límite de 512 MiB de *old space* de V8 no limita todo Node: quedan buffers externos, SQLite, código nativo, supervisor y demás procesos. Los límites de captura se aplicaron a diagnóstico, no al contexto del modelo. Fuente: [informe y alcance](CURRENT_STACK.md). No hay mediciones Windows ni presupuesto de RAM publicado para este producto.

### P · Instrumentación y unidades

| Magnitud | Obtención y lectura correcta |
|---|---|
| Memoria de cada proceso | Identificar PID + hora de creación y rol: supervisor, CPA, CLI y servidor OmniRoute, OpenCode, MCP/terminal, navegador/renderer/GPU WebView2. [PSAPI](https://learn.microsoft.com/en-us/windows/win32/psapi/process-memory-usage-information): working set actual/pico (residente), private bytes/`PrivateUsage` (compromiso privado); working set privado con contadores Windows cuando esté disponible. MiB binarios. No llamar «RAM utilizada» a memoria virtual reservada. |
| Total atribuible | Sumar compromiso **privado** de los procesos propios vivos en la misma muestra; registrar commit del sistema y disponible. Working sets incluyen DLL y páginas compartidas, no se suman como exclusivas. Mostrar WebView2 compartido/atribución incierta aparte, nunca cargar todo Edge al proyecto. Job contabiliza descendientes, no todo proceso del navegador. |
| Heap JavaScript y nativo | En laboratorio con carga sintética y consentimiento: Node/V8 `heapUsed`, `heapTotal`, `external`, `arrayBuffers` (este último puede estar incluido en `external`); registrar heap tras reposo y GC observado. Comparar con private bytes y eventos de asignación nativos vía ETW/WPR por proceso. Bun/OpenCode, Go CPA y WebView tienen allocators distintos: usar métricas soportadas por su runtime en build de diagnóstico; si no existen, «no disponible». RSS menos heap no mide heap nativo. Sin inspector/pprof accesible en producción. |
| CPU y recursos retenidos | Diferencia de tiempo kernel+usuario / tiempo transcurrido (indicar si se normaliza por nº de CPU lógicas), handles, hilos, procesos, conexiones, E/S, tamaño de logs y coste del propio monitor. Congelar paneles inactivos o destruir su controlador; demostrar liberación de suscripciones, timers, watchers, PTY y streams. No confundir caché recuperable con fuga. |

**P · Protocolo reproducible:** misma máquina, build Windows/WebView2, CPU/RAM, plan de energía, versiones, perfil nuevo, dataset, secuencia de turnos, contexto, herramientas y proveedor sintético determinista. Registrar versión/estado del antivirus y procesos externos relevantes sin enumerar datos del usuario. Comparar A (Tauri + web oficial) y B (Electron oficial con los mismos gateways) y cada componente solo. Separar arranque frío y caliente y tiempo hasta salud, catálogo y primera interacción; tres repeticiones por escenario. Equipo dedicado para tendencias: el runner compartido no da un presupuesto de producto.

1. Diez minutos sin UI de agente, diez con workspace inactivo y diez con un panel de administración; probar minimizar, cerrar panel y volver a abrir 20 veces. Contar servidores y renderers antes/después.
2. Carga de 4 h y ensayo nocturno de 8 h: sesión larga con contexto completo, streaming, herramientas, proyecto grande y MCP; después ventana de reposo de 15 min. Repetir abrir/cerrar proyectos y cancelar turnos. Comparar curvas por PID/generación y pendientes de private bytes y heap tras reposos equivalentes, no solo el pico.
3. Muestreo propuesto cada 60 s normalmente, 5 s en ensayo; nunca un evento en disco por token. A/B con monitor apagado/encendido y con panel de logs abierto/cerrado. Medir p50/p95 de CPU en reposo, pico, pendiente MiB/h, bytes escritos/h y retraso del primer evento. Buffer circular y rotación con presupuesto inicial de 3 × 2 MiB por flujo diagnóstico; medir pérdida de eventos, no bloquear inferencia por un visor lento.
4. Interrumpir proceso padre, suspender/reanudar Windows, salir y actualizar con streams activos. Verificar retorno a cero de procesos exclusivos, puertos y handles del supervisor, o explicación de recursos compartidos que continúan. Nunca terminar un proceso del sistema para conseguir esa cifra.

**Criterio de decisión:** publicar tabla con baseline, dispersión entre repeticiones y resultado por escenario antes de fijar presupuestos RAM/CPU. Duplicar servidores, perder permisos/contexto, registrar cuerpos, crecimiento repetible sin meseta después del reposo o retener árboles tras salida bloquea promover el candidato hasta explicar/corregir la causa. Una subida de working set aislada no demuestra una fuga. Priorizar eliminación de duplicados, buffers y vistas ociosas sobre cambiar de framework por intuición.
